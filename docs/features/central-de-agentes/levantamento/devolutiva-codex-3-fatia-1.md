2. Pontos frágeis pedidos
1. Locks e escritores. A escolha do lock é coerente: INSERT/UPDATE/DELETE tomam ROW EXCLUSIVE, que conflita com SHARE ROW EXCLUSIVE; assim, um escritor em andamento termina antes da conferência, e o seguinte espera. Documentação PostgreSQL. Inferência: uma exclusão concorrente de organização pode produzir inversão de ordem entre locks de conexões/agentes e da tabela de prompts. O teste de cascata da Task 2:1098–1128 é sequencial e não mede isso. Um deadlock abortaria uma transação, sem autorizar indevidamente a ligação.
2. Visibilidade após espera. A RPC PL/pgSQL não declara STABLE (Task 1:629–642). Sob READ COMMITTED, a função VOLATILE usa snapshot novo em suas consultas, e FOR SHARE espera a atualização concorrente da linha; a leitura posterior pode ver o valor confirmado. Volatilidade, locks. A prova executável dessa corrida continua pendente.
3. Vercel. VERCEL_GIT_COMMIT_SHA é disponibilizado ao runtime quando a opção de variáveis de sistema está habilitada; a Task 13:4332 confere isso. Documentação Vercel. As rotas de API usadas para alias e deployment existem. A implementação, porém, não confere projectId devolvido pelo alias, só verifica um domínio e pode deixar a ligação ativa se o pós-check falhar. Um deployment mais novo READY, mas ainda não promovido, também será tratado como “rollback” pela Task 10:3536–3545: é uma recusa conservadora, não um falso CONFERE. Alias API, promoção de deployments.
4. Falha ao inserir evento e prova antiga. Na versão @supabase/supabase-js 2.89.0 fixada pelo 335f32b:package-lock.json:3773–3775, falhas usuais de rede do PostgREST são convertidas em { error } sem .throwOnError(); a Task 8:2655–2663 as registra e segue. Código do SDK na versão fixada. Ainda assim, a função de prova pega o último evento registrado, que pode anteceder uma resposta entregue cujo insert falhou (Task 1:608–613). Inferência concreta: evento A, entrega B sem evento, retorno do prompt a A → o script pode dizer CONFERE para A, embora a última entrega tenha sido B. Nesse exemplo o prompt atual também é A; não encontrei, só com essa falha, prova de que o agente ficaria diferente do prompt atual. A afirmação “última resposta entregue” continua sem garantia.
5. Limpeza de metadata legítimo. A mudança é real: Task 9:3242–3255 remove seis nomes também de metadata manual/n8n. Nas rotas internas examinadas não identifiquei um produtor de UI que dependa desses seis nomes. Os fluxos n8n externos não foram inspecionados; a leitura prevista antes da publicação (Task 13:4351–4352) é necessária para fechar esse impacto.
6. Promise.race de 400 ms. Não prova que a RPC esperou um lock. Uma chamada que só começou depois dos 400 ms pode receber o resultado esperado após o COMMIT, deixando o teste verde sem exercitar a trava (Task 2:840–843, 1335–1341, 1365–1370). A correção é sincronizar as sessões e observar o wait por lock, por exemplo com pg_stat_activity/pg_locks, antes de liberar a primeira transação.
3. Novos achados, em ordem de gravidade
1. Bloqueante — o primeiro push da prévia não tem bloqueio de build demonstrado. Evidência: Task 13:4337 presume que um commit vazio com [vercel skip] evita o build, justamente quando as variáveis genéricas de Preview apontam ao banco de produção; 4338–4339 só configura as variáveis da branch depois. O PLAN não define Ignored Build Step ou git.deploymentEnabled. A Vercel documenta build por push como padrão e essas configurações como mecanismos para evitá-lo. Builds, configuração Git. Inferência condicionada à configuração real, que não vi: o primeiro push pode criar uma prévia acessível com credenciais de produção. Correção: antes do push, comprovar e registrar o mecanismo de bloqueio configurado no projeto; preferencialmente desabilitar o auto deploy da branch, criar a branch e suas variáveis, reabilitar e disparar o deploy explicitamente. Não usar só a mensagem do commit como gate.
2. Bloqueante — teste “local” pode consultar banco remoto por PostgreSQL direto. Evidência: a guarda verifica a URL REST local (Task 2:825–829), mas DB_URL aceita qualquer SUPABASE_DB_URL (831) e sessaoPg() conecta nela (956–959); as corridas fazem INSERT/UPDATE/DELETE (1331–1343, 1362–1365). O runner herda o ambiente e não substitui SUPABASE_DB_URL (335f32b:scripts/test-local.mjs:52–63). Correção: validar host, porta e database da URL PostgreSQL como locais antes de criar fixtures ou abrir sessão, ou eliminar o override. Um valor remoto deve falhar fechado.
3. Bloqueante — erro no pós-check deixa a conexão ligada. Evidência: Task 11:4252–4265 liga e só depois chama lerPublicacaoNoAr; falha HTTP nessa leitura lança (Task 10:3493–3496) e cai em main().catch (Task 11:4269–4271), sem executar desligarConexao. Correção: tratar qualquer erro ou resposta inconclusiva do pós-check como motivo para desligamento, verificar a linha depois, e abortar a publicação se não conseguir confirmar ai_agent_id = null. O desligamento compensatório deve ser condicionado ao agente recém-ligado; hoje a atualização por ID pode apagar uma ligação concorrente diferente (Task 10:4053–4062).
4. Bloqueante para usar CONFERE como autorização geral de produção — identidade e tráfego da publicação não estão completos. Evidência: Task 10:3520–3527 ignora o projectId do alias; Task 11:4203–4227 aceita qualquer par banco/domínio informado; Task 13:4363 prova apenas crm.basea2.com. Inferência condicional: se o outro domínio de produção apontar a outro deployment, ou se houver Rolling Release, a consulta a um alias pode indicar A enquanto parte do tráfego recebe B. A API do alias inclui projectId; a documentação de Rolling Releases descreve a divisão de tráfego. Correção: vincular ref do banco a projeto e lista fechada de domínios, conferir todos os domínios de produção e recusar ligação durante rollout ativo. Não observei a configuração real desses domínios ou de Rolling Releases.

Evidência: Task 8:2643–2663 apenas avisa se o insert falhar; Task 1:608–613 sempre devolve o último registro existente; Task 10:3845–3852 pode classificá-lo como CONFERE; a janela de frescor foi retirada (SPEC:422). Correção: reconciliar a prova com respostas nativas posteriores gravadas em conversation_messages, bloquear a ligação se houver lacuna e exigir uma resposta real nova depois de qualquer falha de registro. Um limite de frescor ajuda, mas sozinho não detecta uma lacuna recente.

Correção: nesse caso, esperar 400 e zero chamadas; em outro caso, mandar payload válido e verificar que o executor não recebe replyEvent.
