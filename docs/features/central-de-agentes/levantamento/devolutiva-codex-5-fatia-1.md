Ele observa o destino do pedido, não confirma que a autenticação está funcional.
3. Achado 12 — resolvido no desenho, pendente de prova real. Evento, função SQL e prova comparam commit e deployment (PLAN:527, 627–639, 769–779, 2765–2768, 4375–4383). A Vercel documenta VERCEL_DEPLOYMENT_ID em tempo de execução. No rollback instantâneo, o alias volta a um deployment existente; promover uma prévia para produção envolve novo build. Não encontrei, nesses dois casos, um motivo para o ID em execução ser o ID de outro deployment. Uma requisição encaminhada a uma versão antiga por Skew Protection gravaria o ID antigo e a comparação recusaria a prova — inferência a partir do roteamento documentado. A igualdade real continua sendo um gate do Step 1.5. Variáveis de sistema, rollback, promoção, Skew Protection.
4. Achado 13 — parcial. O PLAN escolhe pasta fora da sincronização, EFS, conferência posterior e retenção (PLAN:5298–5316), mas os comandos de dump não apontam para essa pasta. Ver achado novo 1.
5. Achado 1 da 3ª rodada — parcial. A URL de banco da branch é checada antes do push, e os clientes de produção lidos em 335f32b usam NEXT_PUBLIC_SUPABASE_URL. Porém o helper pode terminar com OK mesmo imprimindo divergência da chave anônima. Ver achado novo 3.

O G23 exige ambos: restauração testada e agente sem poder destrutivo direto em produção (SEGURANCA-GATES-VIBE-CODING.md:162–165).
2. Pontos frágeis que restam
1. A afirmação da prova está corretamente limitada no texto. Um evento de D, com commit, chave, origem e SHA iguais, serve como testemunha do texto usado por aquele deployment com as leituras do banco funcionando (SPEC:178–189). CONFERE em produção não autoriza ligar: o comando continua recusado nesta fatia por faltar a conferência do endereço do webhook na Evolution (SPEC:191; PLAN:4935–4938). A leitura transitória do override e a morte do processo entre ligação e conferência permanecem limitações declaradas, não provas de equivalência nesses casos.
2. A janela entre leituras continua existindo. ligado descreve a linha na releitura final; outra operação pode alterá-la depois. incerto é a saída correta quando essa releitura falha (PLAN:4730–4740). Não encontrei nesse fluxo uma saída que afirme ligado sem observar o agente esperado.
3. O endpoint de migration é documentado, mas seu acesso não foi provado para este token. A referência oficial especifica POST /v1/projects/{ref}/database/migrations com resposta 200; o ensaio no banco de teste é o gate para saber se a credencial concreta tem acesso. API de migrations.
3. Achados novos, por gravidade
1. Bloqueante — os dumps podem ser gravados fora da pasta cifrada. O PLAN prepara C:\Users\PC Gamer\BaseCRM-dumps\<data>\, mas usa -f roles.sql, -f schema.sql e -f data.sql sem mudar o diretório de execução (PLAN:5299–5309). **Inferência:** se executados do repositório, esses caminhos relativos põem dados pessoais ali, antes de qualquer conferência por cipher. Além disso, icacls /inheritance:r /grant:r <usuário> não remove permissões *explícitas* preexistentes de outros usuários; a alegação “só da conta dele” precisa ser conferida. **Correção:** passar caminhos absolutos sob a pasta EFS nos três -f; antes e depois do dump, conferir EFS e ACL efetiva da pasta e dos três arquivos, recusando qualquer destino ou permissão divergente. CLI do Supabase, semântica do icacls.
2. Bloqueante para marcar G23 como PASS — a restrição de escrita não é imposta. aplicar_migration.py aceita qualquer ref de 20 letras, qualquer arquivo com nome no padrão e qualquer SHA fornecido pelo próprio operador, desde que igual ao arquivo (PLAN:5211–5229); usa o token de gerenciamento para aplicar a migration nesse ref (PLAN:5230–5240). Repetir o ref em --confirmar-banco não limita projetos nem fixa o artefato já ensaiado. Correção: fixar refs, caminho e SHA aprovados em uma entrada verificável; executar a etapa de produção por operador ou por mecanismo que não entregue ao agente uma credencial capaz de enviar SQL arbitrário. Um PAT limitado ao projeto reduz o alcance, mas sozinho não elimina poder destrutivo direto. Até lá, registrar a escolha por processo como exceção residual, sem chamar G23 de PASS. A API oferece PAT com escopo por projeto e permissão. Autenticação da Management API.
3. Importante — falha excepcional do registro de evento pode marcar como falha uma resposta já entregue. registrarEventoDeResposta trata { error }, mas não captura rejeição ou exceção do insert (PLAN:2784–2811); seu chamador o aguarda depois do envio e do insert das mensagens (PLAN:2846–2859). Em 335f32b:app/api/public/channels/evolution/[connectionId]/webhook/route.ts:259–334, uma exceção nessa chamada entra no caminho que registra falha de entrega. Inferência condicionada: isso ocorre se o cliente lançar em vez de devolver { error }; os testes planejados só simulam o segundo caso (PLAN:2598–2604, 2722–2729). Correção: capturar a exceção dentro do registrador, avisar sem propagá-la e testar explicitamente um insert rejeitado.
4. Importante — o helper pré-push admite OK com chave anônima divergente. Para NEXT_PUBLIC_SUPABASE_ANON_KEY ausente, ilegível ou com ref errado, ele apenas imprime a condição; só a URL acrescenta erro a falhas (ler_env_ensaio.py:125–155). O código em 335f32b:lib/supabase/client.ts:7–10 e lib/supabase/server.ts:13–15 ainda prefere NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY, que o helper não valida pelo valor. Isso não muda o destino da URL de teste, mas invalida a afirmação de que saída 0 confere a chave usada e o funcionamento do login. Correção: fazer divergência ou ilegibilidade da anon falhar quando ela for parte da prova; no prova_login.py, conferir também a resposta do serviço de autenticação com a chave efetiva, distinguindo credenciais inválidas de chave de API inválida (PLAN:5112–5120).
5. Importante — falta recuperação para migration aplicada e alinhamento da versão falho. O POST e o UPDATE supabase_migrations.schema_migrations são operações separadas (PLAN:5239–5255). Se o POST aplicar e o alinhamento falhar ou perder a resposta, a próxima execução recusa o nome já registrado (PLAN:5235–5237), sem rito para reconciliar o estado. Correção: definir parada e inspeção somente de leitura nesse caso; permitir alinhamento posterior apenas após conferir no histórico que o SQL aplicado é exatamente o arquivo aprovado. Nunca repetir o POST às cegas.
6. Menor — número excluído é relatado como linha existente sem agente. lerAgenteDaConexao distingue { existe: false }, mas conferirLinha junta ausência da linha com ai_agent_id nulo (PLAN:4620–4627, 4652–4656). A CLI pode então dizer “linha conferida” e “número não está ligado” para uma conexão que já não existe (PLAN:4737–4738, 4972–4974). Correção: estado conexao_inexistente separado e mensagem correspondente.
